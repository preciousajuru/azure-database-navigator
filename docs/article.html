Azure SQL, PostgreSQL, MySQL or Cosmos DB: How Do You Choose the Right Database on Azure?

By Precious Ajuru · 1 November 2026

Start with the data, not the service catalogue. What must the application read and change together? What has to stay compatible with an existing engine? Where do users need data, and how much recovery work can the team own? Those answers make a useful shortlist. A language, a JSON payload or an “AI” label does not.

Azure has a broad data platform, and the names can make unlike things sound interchangeable. A database engine, a database service, an API that resembles another product, a cache and a search index each solve different problems. Most importantly, one application can need more than one of them.

For business transactions, begin with a relational model

Consider customers, orders and payments. The application needs related records, joins, constraints and changes that must succeed or fail together. That is a relational workload. The first question is which relational engine and operating model fit the application—not whether its team writes C#, JavaScript or Python.

Microsoft’s data-model guidance describes relational stores as suited to transactional data, integrity constraints and rich SQL queries. Azure SQL Database and Azure Database for PostgreSQL Flexible Server are sensible starting candidates for a new application like this. Compare their engine features, drivers, team experience and integration requirements. Do not select one by language.

MySQL Flexible Server is also a relational database, but it is usually most relevant when the application or migration needs the MySQL engine and ecosystem. A relational recommendation does not mean every relational engine is compatible with every other one.

Azure SQL Database, Managed Instance and SQL Server on VMs are not one choice

“Azure SQL” covers different deployment models. Azure SQL Database is a managed, database-scoped option for application databases. Its configuration can include choices such as serverless compute, provisioned compute, elastic pools and service tiers; those are not interchangeable defaults. Choose a service first, then validate the configuration against measured workload needs.

Azure SQL Managed Instance offers a managed SQL Server instance model. It is worth assessing when a migration depends on documented instance features. Microsoft’s Azure SQL decision tree calls out SQL Agent, CLR, linked servers, cross-database queries and transactional replication as factors to investigate for Managed Instance.

Need operating-system or file-system access, or a specific SQL Server version? The same decision tree points to SQL Server on Azure VMs. That control comes with a different operational burden. Decide who owns patching, backups, monitoring, high availability and disaster recovery. An existing SQL Server running on a VM does not, by itself, require a VM target.

For migration, inventory the actual dependencies first: engine version, jobs, extensions, drivers, linked servers, SQL modes, collations, plugins and operational scripts. Then test the required features against the exact Azure service and configuration. “Nearly compatible” is not a migration test.

PostgreSQL and MySQL are engine decisions

Azure Database for PostgreSQL Flexible Server is a managed PostgreSQL service with configurable compute and server settings. If the application depends on a PostgreSQL extension, check its exact name and version against the current extension allow-list. A product description that mentions extensions is not proof that your extension is available in your region or configuration.

Azure Database for MySQL Flexible Server is managed MySQL. It may be a reasonable destination for a MySQL application, but do not describe it as a drop-in replacement for every MariaDB workload. The Azure Database for MariaDB managed service retired on 19 September 2025; that service retirement does not mean the MariaDB engine itself has retired. For example, a WordPress site using MariaDB should be tested against MySQL Flexible Server: check plugins, schema, SQL behaviour, character sets, drivers, backups and the migration path before committing.

Choose Cosmos DB for its access pattern, not because data is JSON

JSON can be stored in relational databases as well as document databases. Azure Cosmos DB for NoSQL is a document-oriented distributed database with explicit partitioning and consistency choices. Its consistency options trade among consistency, availability and latency; its partitioning model makes data distribution and query shape important design work.

Global users do not automatically require writes in multiple regions. First measure where the clients are, set a latency target, and decide whether reads, writes or both need to be local. Then design partition keys, transactional boundaries, consistency, region placement and throughput together. Compare the result with a relational design if the application has substantial relationships or cross-record transactions.

MongoDB applications need a separate compatibility exercise. Azure DocumentDB is the current name for the vCore-based Cosmos DB for MongoDB offering; RU-based Cosmos DB for MongoDB is a separate choice. A familiar driver or wire protocol is not complete feature parity. Check the DocumentDB version-specific compatibility reference and the RU-based API feature matrix for the commands, aggregation operators, driver versions and migration workflow the application actually uses.

Some data belongs in a different kind of store

A file archive may need Blob Storage and no database at all. A cache such as Azure Managed Redis can reduce pressure on a durable store, but it needs an explicit source of truth, expiry and invalidation strategy. The Azure Cache for Redis retirement dates differ by tier, so check the current notice rather than selecting a legacy tier by habit.

For telemetry, compare time-series and analytical query patterns with services such as Azure Data Explorer or Fabric Eventhouse. For document search or retrieval, Azure AI Search may act as a derived index. A retrieval-augmented generation (RAG) application might use object storage for source documents, a relational database for transactional application state and a search index for retrieval—but only where each role is required. Define how updates, lag, failures and index rebuilds work.

Write down what “reliable” means

Recovery Point Objective (RPO) is how much recent data the business can afford to lose. Recovery Time Objective (RTO) is how long it can be without the service. Put both in writing, then verify backup retention, restore tests, high availability and regional recovery for the target tier and region. Do the same for encryption, private networking, data residency and named compliance controls. No service label is a compliance guarantee.

There is no universal “best Azure database”. There is a shortlist that fits a defined workload, a set of compatibility tests, and a list of configuration decisions still to make. Azure Database Navigator turns those inputs into an explainable starting point. Treat its result as a guide for engineering review, not a substitute for one.
